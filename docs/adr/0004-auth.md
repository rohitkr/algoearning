# 0004 Auth: Clerk behind an adapter

**Decision.** Clerk (free tier) for sign-up/sign-in (Google + email/password), password reset and
sessions. The API never trusts the browser: it verifies Clerk's signed session JWT on every request and
WebSocket connect, and keeps its own `users` table in sync via Clerk webhooks. All product data
(plans, brokers, strategies, orders) lives in our database.

**Exit plan.** Auth sits behind an `AuthProvider` interface, so it can be replaced by our own
implementation if Clerk's free tier is outgrown.

**Implementation (phase 4).**

- Web: `@clerk/nextjs` with `clerkMiddleware()` in `proxy.ts`; every signed-in page/layout calls
  `auth.protect()` (resource-level checks, per Clerk's guidance, instead of path matching). Clerk's screens use
  our CSS theme tokens, so they follow light/dark automatically.
- API (`ae_api/auth/`): Clerk session JWTs verified locally (RS256 via the instance JWKS, issuer from the
  publishable key, exp/nbf, `azp` must be our web origin, pending sessions refused). Accepted from
  `Authorization: Bearer` or the `__session` cookie. A new user's profile is read once from Clerk's Backend API.
- Users webhook `POST /v1/webhooks/clerk`: Svix signature + 5-minute timestamp window, stored once per event id
  (replays acknowledged, not re-applied); `user.deleted` locks the account (rows kept for audit).
- `X-Dev-User` remains for local development/tests only (DEV_AUTH, refused outside development/test).
